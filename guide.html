Track 01The idea

BGM Mode plays Spotify songs without the singing, so you can study or work to music and none of the lyrics. It is a web app that also installs as a phone or desktop app (a PWA). It is plain JavaScript with no build step and no npm packages.

For each song it takes one of three routes.

  • Official instrumental. Many songs have an official instrumental on Spotify. BGM Mode searches for it and switches to it at the same second of the song.
  • AI remover. When there is no official version, a neural network (UVR MDX-Net “Inst HQ 5”) runs on your graphics card and separates the voice from the music while the song plays. The project's README reports the voice dropping to about 2 % of its level (−33 dB) with the music rebuilt at 21.5 dB fidelity.
  • Fast remover. A lighter method that needs no graphics card. It cancels what sits dead centre in the stereo picture and keeps drum hits. The README reports about −5 dB of voice overall and 10.5 dB fidelity.

The same two live removers can clean the sound of any other browser tab, such as YouTube Music, with no Spotify account. That is Any tab mode.

Why it stays personal

Spotify's developer terms do not allow publishing an app that alters their audio. Development Mode also limits an app to its owner plus up to five people the owner adds. YouTube Music offers no way for another site to read or control it, and its terms forbid separating the audio of what its player plays. So BGM Mode connects to it only through links and through Any tab mode.

Track 03Signing in with Spotify

BGM Mode logs in with the Authorization Code flow with PKCE. A page that runs in a browser cannot keep a secret, so PKCE replaces the client secret with a one-time proof that only this page knows. There is no client secret anywhere in the project.

The steps

  1. The page makes a verifier of 64 random characters and a state of 16, picked from letters, digits and -._~ using the browser's secure random numbers. It saves both, with the Client ID, in session storage under bgm.login.
  2. It sends you to Spotify's authorize page with the Client ID, the redirect address, the requested scopes, the state, and the challenge: the SHA-256 hash of the verifier, written in base64url without padding (method S256).
  3. You approve. Spotify may skip this for a returning user.
  4. Spotify sends the browser back with ?code and state in the address.
  5. The page removes the query from the address and checks that the state equals the saved one. A missing or different state shows “That Spotify login expired” and asks you to try again. Cancelling at Spotify shows “Spotify login was cancelled.” Any other error shows “Spotify login failed” with Spotify's reason.
  6. It posts the code and the verifier to Spotify's token address.
  7. Spotify answers with an access token, a refresh token and a lifetime.
  8. The page stores them in local storage as bgm.auth, and clears the “signed out” flag. “Logged in” simply means a refresh token is present.
  9. Every API call carries the access token.

The redirect address is the app's own folder: the page's origin and path cut after the last slash, the same from either page. It must be registered in the Spotify dashboard exactly.

Keeping the login alive

  • The access token is reused until 60 seconds before it expires. Only one refresh runs at a time per window, and if Spotify sends no new refresh token the old one is kept.
  • If a refresh fails but another open window has saved a newer refresh token, this window uses that one (and its access token, if more than 60 seconds remain). Spotify can rotate refresh tokens, and two windows would otherwise race each other into a logout. When the failure is a 400 or 401 and no newer token exists, the saved login is deleted.
  • Automatic sign-in runs on load when you are logged out, a Client ID is saved, you did not log out on purpose (bgm.signedOut, kept in local storage), and this tab has not already tried (bgm.autoSignIn, kept in session storage, so a failure cannot loop).
  • Log out stops the live remover, disconnects the player, deletes bgm.auth and sets bgm.signedOut. Your Client ID and saved covers stay. Nothing is revoked at Spotify.

Talking to Spotify's API

Every call goes through one small wrapper for https://api.spotify.com/v1. With no token it fails with a “not connected” 401, which the page shows as the login screen. A 401 triggers one forced refresh and one retry. A 429 with a Retry-After of 5 seconds or less waits that long (a missing, zero or invalid value counts as 1 second); a longer one fails at once. A 5xx waits 600 ms. A call makes at most three tries in all, and the refresh after a 401 uses up one of the retries. An empty or non-JSON reply becomes null.

Track 04Official instrumentals

The cheapest way to remove a voice is to not need to: play the version the artist already made without one. Two files do this work. matcher.js decides what counts as an instrumental and which candidate is best. bgm.js decides when to search and how to switch.

Finding the best one

BGM Mode searches Spotify with up to three queries and stops at the first one whose pooled results contain a match. The first names the title, the first artist and the word instrumental. The second drops the artist, which finds songs whose instrumental is credited to the composer. The third uses “inst” instead, which is how many K-pop releases are named. Each query asks for 10 results, the most Spotify's Development Mode allows since February 2026, in your own market. The search runs for every new song, whether switching is automatic or you pressed the button, and the answer, including “none”, is remembered for the session.

A candidate is thrown out when any of these is true:

  • it has no address or name, or it is the very track that is playing;
  • Spotify marks it as not playable in your market;
  • its core title (the title with its tags removed) differs from the song's;
  • neither its title nor its album name carries an instrumental marker;
  • its tags say a cappella or vocals only;
  • its tags contain an arrangement word that the original song does not (list below);
  • it shares no artist with the song;
  • its length differs from the song's by more than 8 seconds or 5 %, whichever is larger.

The arrangement words stop BGM Mode swapping a song for a different piece of music that happens to say “instrumental”. Only the tags are checked, and a word the original song also carries does not count against the candidate. Karaoke is accepted, not excluded.

Switching without losing your place

Before anything else the swap stamps the song with the current time, so the same song is not switched again for five minutes when switching is automatic. The button ignores that limit. Then it asks Spotify what is playing. With no active device it stops with an error. If the song has already changed it stops quietly, or, if you pressed the button, says “The song changed, try again.”

The song's position is its last known progress plus the time that has passed since it was read, if it is playing. Inside a playlist or album, BGM Mode queues the instrumental, then looks at the queue up to five times, 300 ms apart, to count songs queued by hand that sit ahead of it. If there are some it leaves the queue alone and says the instrumental will play after them. Otherwise it skips to the next song, which is now the instrumental. If more than 3 seconds had gone by, it confirms the instrumental is the one playing (up to eight checks, 250 ms apart) and seeks to the same second. A single track with no playlist is simply played again from the same position.

When there is no instrumental

  • Live remover (the default). Nothing happens until you press Start, because the browser needs your click to share a tab. Leaving this setting stops the remover.
  • Skip the song. BGM Mode skips ahead, up to 8 songs in a row. The ninth plays, with a notice that no instrumentals turned up in the last eight songs.
  • Play the original. Nothing is done.

Podcast episodes are never searched. The remover rests and the desk says BGM Mode leaves them as they are.

Songs playing on another device

The in-app player reports its own changes at once. For a song playing on your phone or the Spotify desktop app, BGM Mode asks Spotify what plays: every 5 seconds, or every 15 seconds while the in-app player is playing, when it only checks in case playback moved without word. It also asks at start-up, the moment the tab becomes visible again, and 800 ms after a command it sent itself. The question asks for songs and episodes. An answer for its own device is ignored, because the player already knows. Otherwise the song is treated like a local one, including looking for its instrumental and switching it on that device. Its position is advanced every 500 ms between answers.

Track 05The live remover

When there is no official instrumental, or when you point BGM Mode at any other tab, a live remover takes over. It has three parts: a controller on the page (live-remover.js), the engine window (engine.html and engine.js), and two removers that live inside the engine.

From one click to sound

  1. One click. Browsers allow screen sharing only inside a click, so Start runs getDisplayMedia first. You pick a tab, and must tick the box to share its sound. No sound track means an error message.
  2. The engine window opens as a small pop-up (380 by 300 pixels, named bgm-engine). If the browser blocks it, the button changes and a second click opens it.
  3. The stream is handed over by calling the engine window's own functions: attach(stream, params), then setParams whenever the mode, the strength or the sound changes. The two windows share an origin, so no messages are needed. The engine sends reports back the same way.
  4. The engine builds its audio: an AudioContext set for steady playback, a source made from the stream, the chosen remover, the Sound chain, then your speakers.

The share also carries a video track, kept to one frame a second. Its label tells the page which tab you chose.

Two sources, two modes

The source is either this page (app), where Spotify's player makes the sound, or another tab (tab). Start uses this page when you are logged in and another tab when you are not. When the source is this page and an official instrumental is playing, the strength is set to 0 so the music passes through without touching it. Music from another tab is always processed.

The mode is ai only when you chose AI quality, the model has finished downloading, and the browser has WebGPU. Otherwise it is dsp, the Fast remover. The strength sent to the engine is your slider divided by 100.

  • The Fast remover plays while the AI model is still loading.
  • If a model run takes longer than 2.5 seconds, the engine reports that this GPU is too slow for live separation and Fast keeps playing. If the GPU fails later, it reports that the GPU stopped and switches to Fast. AI is not retried in that window.
  • Switching between Fast and AI replaces the audio node outright, so the AI path is silent for a moment until its buffer fills.

Why a separate window

If the page played its own processed sound, the share would capture that sound again, creating a feedback loop, and the muting would silence the processed output along with everything else. The engine window has its own audio output, outside the share. It stops when any shared track ends (you press Stop sharing), when you press Stop, or when the window closes, which the page checks once a second.

Track 06The AI vocal remover

The AI remover uses a trained neural network in place of arithmetic. It is the “MDX-Net Inst HQ 5” model from the Ultimate Vocal Remover project (UVR). The model takes a short slice of music drawn as a picture of its frequencies over time, a spectrogram, and returns the same picture with only the instruments in it. The rest of this track is everything wrapped around that one step: getting the sound into a spectrogram, running the model fast enough to keep up with a song, and turning the answer back into sound.

Where the model comes from

  • From the local server (npm start). The page can ask the server to download it. The request must come from the app's own address. The server fetches the UVR release file from GitHub, hashes it while writing a .part file, and renames it only if the hash matches. On any failure the partial file is deleted. A file already present at start-up is trusted without hashing again.
  • Straight into the browser (no server needed). The page tries a copy on Hugging Face (nomadkaraoke/public_uvr_models), then another (Politrees/UVR_resources). It hashes the whole file with the browser's SHA-256. A mismatch moves on to the next copy. A match is stored in Cache Storage under bgm-mode-model, which the service worker keeps across app updates.
  • Loading reads that cache first and otherwise takes the server's file, which it then caches without a hash check.

Before the first real run the engine does one untimed run on silence, which makes the GPU compile its programs. It then times three runs back to back and keeps the slowest as the run time that pacing depends on.

From sound to spectrogram and back

  1. Resample to 44.1 kHz. Sound cards usually run at 48 kHz, so the engine converts the captured sound. The resampler is a windowed-sinc design read from a table: 32 taps either side, 256 phases with linear interpolation between them, a Blackman window, and a cut-off of 0.97 of the lower Nyquist frequency. It adds no time shift and passes sound through untouched when the two rates already match.
  2. Short-time Fourier transform (STFT). The sound is cut into frames of 5120 samples, one every 1024, each weighted by a Hann window and centred on its place in the song. Left and right are packed into one complex FFT (left plus i times right) and separated afterwards, which halves the work. 5120 is 5 times 210, so the FFT is a mixed-radix one.
  3. Model input. A tensor of 32-bit numbers shaped [1, 4, 2560, 256]: four channels (left real, left imaginary, right real, right imaginary), 2560 bins, 256 frames. Bins 0 to 2 are set to zero, as UVR does. The top bin is never written, so it is zero in the output.
  4. The model runs on the GPU and returns a tensor of the same shape: the music.
  5. Mixing by strength. With your strength slider as s between 0 and 1, every real and imaginary value becomes the formula below. At s = 0 the model is skipped.
  6. Inverse STFT. The frames are overlap-added with the window and divided by the summed squared windows, which restores the right loudness.
  7. Resample back to the sound card's rate.
output = mix + s × (1.01 × model − mix)

Streaming: a sliding window

The model wants almost six seconds at once, but music keeps arriving. So every run looks at the latest 256 frames (5.94 seconds), and contributes only a small step of new output. The newest 12 frames are held back as look-ahead, so the model always has sound after the part it is cleaning.

The details, from separator.js:

  • A frame is computed the moment its last sample arrives and goes into a ring of 256 slots.
  • When no run is in flight, a new one starts once the newest frame, minus the 12 frames of look-ahead, is at least one step ahead of what has already been output. This is checked again after every run.
  • Where two outputs meet, one extra hop (1024 samples) is cross-faded with a raised cosine, r = 0.5 − 0.5 · cos(π (i + 0.5) / 1024), so there is no click.
  • If the engine ever falls more than a whole window behind, the gap is filled with silence and the output jumps ahead.

How often the model runs

The step is chosen from how long a run takes, in stepFramesFor. A run must finish before the next one is due, with 30 % to spare. When it can, the GPU rests twice as long as it works, so a laptop stays cool. But runs are never more than 0.6 seconds apart, because every extra second of step is a second of delay behind the player. In symbols, with the run time in seconds:

The delay behind the player

The look-ahead is (12 × 1024 + 2560) / 44100 = 0.337 s: twelve frames, plus half of one 5120-sample window because frames are centred. The README measures 1.3 to 1.5 seconds on an RTX 4050 at its usual 0.3 s a run, and about 2.6 seconds when runs take 0.3 to 0.9 seconds, measured in headless Chrome. When playback starts, the engine replaces its estimate with the measured gap between what was captured and what has been played.

Keeping the sound from running dry

Processed sound lands in a playback buffer on the audio thread (playback-fifo.js) that holds up to 30 seconds. Playback starts only once a safety margin of sound is waiting. The engine sets the margin to half a model run, never below 0.12 s or above 0.5 s. If the buffer ever runs empty, it plays silence, tells the engine, and waits for the margin again. The engine answers each such underrun by lengthening the margin by 0.1 s, up to 1 s. If the buffer overflows, the oldest sound is dropped. Until the engine sends a margin the buffer uses 0.12 s, capped at 2 s.

Track 07The Fast remover

The Fast remover needs no model and no GPU. It runs inside the audio thread (dsp-core.js, wrapped by vocal-remover.worklet.js) and is classic signal processing. A lead singer is almost always mixed dead centre, so the voice has the same level and the same phase in both speakers. Most instruments are spread to one side. The remover finds the frequencies that look centred and subtracts only those.

Step by step

  1. Cut the sound into frames. An FFT of 4096 samples every 1024 (75 % overlap), each weighted by a Hann window. The whole remover adds 4096 samples of delay: about 85 ms at 48 kHz.
  2. Score every frequency for “centredness”. Three numbers, each between 0 and 1, multiplied together, from statistics smoothed over about 70 ms:
    • balance: 1 when left and right are equally loud at that frequency;
    • coherence: 1 when they carry the same waveform;
    • in-phase: 1 when there is no phase offset between them.
  3. Turn the score into a mask. The score is smoothed a little across neighbouring bins (a quarter, a half, a quarter), then passed through a smoothstep between two thresholds, and multiplied by the strength and by the band weight. With the fixed reach of 0.5 the thresholds are 0.55 and 0.85. The mask rises quickly when a voice appears (0.6 of the gap each frame) and lets go slowly (0.25), which avoids a warbling sound. The strength itself glides half way to a new value each frame, so moving the slider never clicks.
  4. Protect the bass and the top. The band weight is 0 below 120 Hz, rises smoothly to 1 at 200 Hz, and eases down to 40 % between 9 kHz and 16 kHz. Kick and bass guitar survive, and so do cymbals and air.
  5. Protect drum hits. Kick and snare also sit in the centre, but a hit is sudden and spreads over many frequencies, while a sung note is a few steady harmonics. Below 6 kHz the remover compares each bin with its own last seven frames (what is steady) and with the neighbouring ±8 bins (what is spread out). A bin that stands out the way a broadband hit does gets a drum score, and the mask is multiplied by one minus that score. The protection fades out between 3.5 kHz and 6 kHz so the “s” and “t” sounds of a voice are still removed. The README reports that a centred snare keeps about 8 dB more of each hit this way.
  6. Subtract. For each frequency the centre part, mask × the quieter channel's size, carrying the phase of the left-plus-right sum, is subtracted from both channels. It can never be louder than the quieter channel, so a sound panned to one side survives.
  7. Guard against mono. A mono song is all centre, and removing the centre would leave nothing. The guard compares the energy of left minus right with left plus right, each smoothed. Under 0.001 (−30 dB) after the first four fresh frames it declares the song mono and sets the strength to 0; above 0.003 it declares stereo again. Anything quieter than about −80 dB resets it between songs. The flag goes to the page, which says so in the live-remover line.

The strength slider sets the strength directly (a percentage divided by 100). The reach is fixed at 0.5. A note in the code records that it could be widened near the top of the slider for stubborn vocals.

Track 08Shaping the sound

Once the vocals are gone, the music can be shaped. The Sound panel has five tone controls named for what they do to a song, a stereo width control called Space, and twelve ready-made styles. The chain that applies them lives in sound.js, the panel in sound-panel.js, and the landing page's preview in sound-demo.js.

The chain sits inside the engine window, between the remover and your speakers, so it shapes whatever the live remover plays. The Sound button is hidden in browsers that cannot run the live remover.

How each part works

  • Shelves and peaks. A shelf lifts or cuts everything below (or above) its frequency. A peak lifts or cuts a band around its frequency, narrower for a higher Q. The tone sliders move in steps of 1 dB.
  • Space. Call the setting w, from 0 to 2 (the percentage divided by 100). Each speaker gets (1 + w) / 2 of its own side plus (1 − w) / 2 of the other. At 100 % that changes nothing, at 0 % both speakers carry the same mix (mono), and at 200 % the other side is subtracted at half strength, which pushes the stereo image wider. Space moves in steps of 5.
  • Headroom. Boosts make a song louder and can push it past full scale. The chain turns the song down first by half of the biggest boost plus 3 dB for each 100 % that Space goes above 100. That is 0 dB for flat settings and at most 9 dB (a 12 dB boost and Space at 200 %). Cuts need none.
  • Limiter. A compressor set as a limiter, with a threshold of −2 dB, no knee, a ratio of 20, an attack of 1 ms and a release of 0.25 s. It only catches peaks. Web Audio's compressor always adds make-up gain, which for these settings is 1.14 dB, so a trim of 0.877 (−1.14 dB) takes it off again. A Flat setting therefore passes the music at the level it was recorded.
  • Safety. Numbers outside a control's range are clamped, and a missing or broken number is treated as flat.

Track 09The album wall

Behind both pages is a wall of album covers on a tilted plane. Each column of covers slides along the plane forever, every other column the other way, so on screen the covers drift diagonally. It is a single canvas, drawn in a background worker so the covers keep sliding evenly however busy the page is.

The plane

The plane is leaned back 34 degrees, turned 24 degrees and viewed with a perspective of 1400 pixels, which is the same picture CSS would draw for rotateX(34deg) rotateZ(24deg). A column slides one cover along every 6 seconds. The size of a cover scales with the window: its edge is 10.5 % of the window width, kept between 132 and 196 pixels, with a gap of 14 % of that between covers. In a 1440-pixel window that is 151-pixel covers, a 21-pixel gap and a 172-pixel pitch.

The plane has to be big enough to fill the window at every moment. The code projects the window's four corners onto the plane, adds one cover's pitch on every side, and divides by the pitch to get the number of columns and rows. A column holds its covers twice and slides one full loop at a time, so it is never short. Column starting points are staggered by the golden ratio (0.618034 of a loop per column), which spreads them evenly with no visible pattern. A cover never sits directly above or below itself, even where a column's list starts over, and each column carries on from where the one before it ended, so a big set of covers is all used before any repeats.

How a frame is drawn

  • All the covers sit on one sprite sheet (4-pixel gaps, 6-pixel rounded corners) held as an ImageBitmap, so drawing a cover is one cheap copy. Covers reach the painter as 300 by 300 bitmaps, and the canvas's pixel ratio is capped at 1.5.
  • On the landing page a second copy of the sheet is toned with sepia(0.18) saturate(0.85) to sit on the cream page. The hovered cover keeps its own colours.
  • One shared soft shadow image is drawn 8 pixels below every cover. Each frame draws all the shadows, then all the covers, then the lifted cover.
  • A hovered cover rises 40 pixels, easing with a time constant of 0.12 seconds. Its shadow stays on the wall and darkens as the cover rises.
  • A new set of covers fades in over the old for 1.1 seconds. The wall starts and stops like a platter, easing with a time constant of 0.5 seconds.
  • It slides only when moving is on and it is neither paused nor still. It stops asking for frames when it is off screen or at rest. Reduced motion makes it still, and the player also pauses it when its window loses focus.

The page and the worker

If the browser can hand a canvas to a module worker (the page tests this first), the canvas is transferred to album-wall-worker.js as an OffscreenCanvas. Otherwise the same painter runs on the page. The two sides talk in messages:

Getting the mouse to the wall

The wall is behind the page, so the page must work out when the mouse is really over it. It walks down the stack of elements under the pointer (elementsFromPoint) until it reaches the canvas, and gives up at any element outside the wall that is not the page or the body or marked as see-through (the landing page marks its layout boxes). Only a real mouse counts, at most once per animation frame, and the check runs again when the page scrolls.

A click counts when a left-button press and the click that follows are within 6 pixels of each other and nothing is in the way. The page sends pick, and the painter answers picked with the cover and the version of the set it was drawn from. The page ignores an answer about an older set, which can happen if the covers change while the message is in flight. In the player, a pick plays the album starting at that song, on the in-app device once it is ready. The landing page gives the wall no pick handler, so clicking does nothing there.

Where the covers come from

After login the player asks Spotify for your last 50 recently played songs, your top 50 tracks of the last month or so (the short-term list), and your queue with the song now playing. It keeps one cover per album, at most 48, using the last-listed picture that is at least 250 pixels wide (or the first if none is). The set is saved in local storage (bgm.covers, secure addresses only) and shown first next time. Fresh covers replace it on screen only when none were saved or none had an address to play.

Keeping the frame rate steady

The wall and the turntable share a frame pacer (frame-pacer.js). On a screen that refreshes faster than 60 Hz it draws on every Nth refresh, with N the largest number that still keeps 60 frames a second. It learns the refresh rate from the median of the last 15 gaps between refreshes, ignoring gaps over 100 ms, which are the animation sleeping rather than the screen.

N = max(1, floor(1000 / refreshMs / 60 + 0.05))

Track 10The turntable

The now-playing desk is a record player. The record spins while a song plays, and the tonearm sits on a groove that matches how far into the song you are. You can drag the arm to seek. All of the motion is plain arithmetic in turntable-motion.js, and turntable.js connects it to the page.

The record

The record turns at 200 degrees a second, which is 33⅓ revolutions a minute. It eases up to speed with a time constant of 0.45 seconds and coasts to a stop over 0.7 seconds, counting as stopped below 2 degrees a second. A frame that arrives after a long gap, such as a hidden tab waking up, moves things no further than 0.1 seconds.

The arm

The arm's angle, its lift and its follow-the-pointer motion are all critically damped springs: the fastest way to reach a goal without overshooting. They are solved exactly rather than step by step, so they stay stable at any frame rate. The stiffness numbers are per second:

The three springs
SpringStiffnessFeel
Swing11a full swing takes about half a second
Held30while you drag, the arm trails the pointer by about 1/30 s
Lift28raising or lowering the needle takes about a fifth of a second

The needle never drags across the record. For a real move of more than 1.2 degrees the arm lifts first, swings once the needle is up (at 0.85 of full lift), and lowers when it is within 1.2 degrees of its goal and slower than 6 degrees a second. The slow creep of a playing song stays in the groove. While you hold the arm, it stays raised and follows your pointer.

Song position to arm angle, and back

The groove at song progress p (0 at the start, 1 at the end) has radius 0.42 − (0.42 − 0.205) × p, because the spiral's pitch is even. The arm angle that puts the needle on that radius comes from the law of cosines in the triangle made by the pivot, the record's centre and the needle, using the arm's length. Going the other way, the needle's position gives a distance from the record's centre, which gives progress. When the needle is off the record, progress is unknown, and the cue time on the desk follows the needle.

Dragging

  • A drag begins after 4 pixels of movement. The arm follows the pointer but is kept between its rest and the last groove.
  • Dropping the needle on the record seeks to that point and plays. Dropping it off the record pauses. Cancelling returns the arm. A plain click toggles play.
  • After you move it, the arm waits up to 2.5 seconds for the player to agree: the same play state and a position within 0.02 of the song's length (2 %).
  • The record's grooves glow gold from the needle's position inward: the page sets --needle to 100 × the groove radius ÷ 0.45 as a percentage, and the stylesheet paints gold rings, rgb(229 174 61 / 0.11), from there to 93.33 %.
  • Drawing uses the same pacer as the wall: every Nth refresh, every refresh while you hold the arm, nothing when everything is still, and a jump rather than a glide under reduced motion.

Track 11Offline and error screens

BGM Mode is built so that it never shows a blank page. If the server is off it still opens from a saved copy. If a page does not exist, or the app fails while starting, an error screen says what happened and how to get back.

The service worker

sw.js saves a copy of the app in the browser so it can open without the server. Its cache is named bgm-mode-v23, and the AI model has a separate cache, bgm-mode-model, so an app update never deletes a 59 MB download.

  • Saving. On install it saves every file the app needs, one by one, ignoring any that fail, and takes over without waiting. It lists 76 files, including every file in src/ (a test fails if one is missing). On activation it deletes every cache except the app cache and the model cache, and claims the open pages.
  • Never touched. Anything that is not a GET, anything from another site, and any address starting /api/ or /models/.
  • Registration. Both landing.js and app.js register the worker.

The 404 and offline pages

404.html has no scripts and is marked not to be indexed by search engines. It carries two messages in one file. The default says “This page isn't on the record” and links to the landing page and the player. When the service worker serves it as the offline fallback it changes one attribute, data-reason, from “missing” to “offline”. error.css then shows “Can't reach BGM Mode” with a hint to run npm start and a “Try again” button. The local server answers any missing address with this page (a plain “Not found” for anything other than GET), and tells the browser not to cache it. Whether Netlify serves it for unknown addresses on its own is stated only in a comment in the file, not set up in netlify.toml.

The crash screen

If the player itself fails while starting, the page would be left empty. crash.js is a plain script loaded before the app's modules, so it works even when they do not. It puts the same error screen over the page, with a record and a raised arm, the heading “The music stopped”, a Reload button and a link “Back to the start”. It appears when:

  • one of BGM Mode's own scripts fails to load (the screen names the file);
  • an error is thrown by BGM Mode's own code, or a promise fails and nothing handles it;
  • or 15 seconds pass and the app still has not called window.bgmStarted(), which it does after its first screen is up.

It ignores pictures and stylesheets that fail to load, errors from other sites' scripts (such as Spotify's player) and everything after the app has started, when the app shows its own notices. If the screen was shown too early, bgmStarted takes it down. The error text goes in as plain text, never as HTML.

Installing it

The web app manifest names the app “BGM Mode”, starts it at its own folder, opens it as a standalone window, and sets the background and theme colour to cream (#f4ebdb). The 192 and 512 pixel icons, gold equaliser bars on an espresso tile, are drawn by tools/make-icons.mjs with no libraries.

Track 12Security

Security here has two jobs: keep other sites and other machines away from the local server, and stop the browser running anything but BGM Mode's own code. The defences are layers, so one failing does not open everything.

The local server

serve.mjs uses only Node's built-in modules. It listens on 127.0.0.1 (Spotify accepts a loopback address over plain http, but not the name “localhost”) on port 5173, or the port in $PORT.

  • Host check. A request whose Host header is anything other than 127.0.0.1 with the port gets a 307 redirect to the same address on 127.0.0.1. A hostile web page that points its own name at your computer (DNS rebinding) cannot talk to the server.
  • Only public files. Anything not matched by an allowlist, any path containing .., any path that cannot be decoded, and any method other than GET gets a 404. The allowlist covers the four pages, the service worker, the manifest, the share image, files in src/ and assets/ by type, the icons, the fonts and the model. Tests, tools, the server itself and the README are not on it.
  • The one POST. /api/model starts the model download, and only when the request's Origin header is exactly the app's own address. Anything else gets a 403. Other requests to that address just return the download's progress, never cached.
  • Every file goes out with the security headers, the right MIME type, a length and no-cache. A file that fails halfway ends only that one response, never the server.

The headers

The same headers come from the local server and from Netlify. A test reads both and fails if they drift apart. The Content-Security-Policy tells the browser exactly where each kind of resource may come from:

What was checked

  • In Chrome, with the AI model running on the GPU and Spotify's player loaded, the policy blocked nothing: zero violations. Signing in survives the round trip to Spotify with the opener policy on, and the engine pop-up still opens.
  • Each new defence was broken on purpose to confirm a test then fails, and the file was restored byte for byte. Most were caught. Two guards in the crash screen and the path-traversal check turned out to be redundant with other defences, so their tests could not fail on their own.
  • With the server stopped, the offline page shows, and the player still opens from the saved copy. With the player's main script blocked, the crash screen shows.
What is not claimed

The login is kept in the browser's local storage, where any script running on the page could read it. The Content-Security-Policy is what limits which scripts may run. A server that keeps tokens out of the browser has not been built. There is also no client secret anywhere to protect, because PKCE does not use one.

Track 14Limits and open points

Limits of the design

  • Spotify. Playing inside the page needs Premium. Development Mode needs the app owner to have Premium and allows at most five other people. Search returns at most 10 results. Spotify's developer terms do not allow publishing an app that alters their audio.
  • Delay. The AI path runs about 1.3 to 1.5 seconds behind the player on the README's RTX 4050 laptop, and more on a busier GPU. It needs a 59 MB download on first use. A GPU that takes over 2.5 seconds a run falls back to the Fast remover.
  • Fast is a compromise. It removes what is centred, so a voice mixed off-centre survives, and a song that is mono is left alone.
  • Browsers. Only Chromium browsers on a computer can share a tab's sound, so only they get the live remover. Safari support is written from the code and Spotify's documentation, which names Safari on macOS as supported without a version. It has not been tried on a real Safari.
  • YouTube Music. There is no connector to its player: only a search link and Any tab mode.

Small mismatches found while writing this guide

  • The README says the resampler converts between 48 kHz and 44.1 kHz. The code converts between whatever rate the sound card runs at and 44.1 kHz.
  • The README says the model runs “about every 0.6 s”. That holds for runs of about 0.2 to 0.46 seconds (see the table in Track 06).
  • A comment in album-wall.css says the landing page puts the wall in two frames. It uses one fixed layer.
  • Comments in turntable-motion.js and matcher.js mention a drawing in index.html, a pop-up and an extension. The arm's drawing is in app.html, and neither of the others exists any more. parseTabTitle in matcher.js is only used by tests.
  • A note in dsp-core.js asks whether the Fast remover's reach should widen near the top of the slider. It is fixed at 0.5.

Statements that rest on a comment, not on a run

  • That Spotify rotates refresh tokens and may skip the approval screen for a returning user: both come from comments in the login code.
  • That a friend list is limited to five people: from the landing page's text.
  • The README's quality figures (−33 dB, 21.5 dB, −5 dB, 10.5 dB, 8 dB) were read, not re-measured.
